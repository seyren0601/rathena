## 1. Two kinds of item data

| | Definition (static) | Instance (persistent) |
|---|---|---|
| Struct | `item_data` (`itemdb.hpp:3460`) | `item` (`mmo.hpp:313`) |
| Source | YAML item DB | SQL `inventory` / `cart_inventory` / `storage` / `guild_storage` |
| Key | `nameid` (`t_itemid`) | row `id` + `nameid` |
| Lookup | `item_db.find(nameid)` → `shared_ptr<item_data>`, `itemdb_search(nameid)` (returns a dummy item if unknown), `itemdb_exists(nameid)` (`itemdb.cpp:3152`, returns `nullptr` if unknown) | `sd->inventory.u.items_inventory[i]` |

### `item_data` (definition)

✅ Fields (`itemdb.hpp:3460-3550`):

| Group | Fields |
|---|---|
| Identity | `nameid`, `name` (AegisName), `ename` (display), `type` (`IT_HEALING`, `IT_USABLE`, `IT_WEAPON`, `IT_ARMOR`, `IT_CARD`, `IT_PETEGG`, `IT_AMMO`, `IT_SHADOWGEAR`, `IT_CASH`…), `subtype` (weapon/ammo type), `view_id`, `look` |
| Economy | `value_buy`, `value_sell`, `maxchance` |
| Stats | `weight`, `atk`, `matk` (RE), `def`, `range`, `slots`, `weapon_level`, `armor_level` |
| Restrictions | `equip` (`EQP_*` bitmask), `sex`, `elv` / `elvmax`, `class_base[3]` and `class_upper` (job masks), `flag.no_equip` (zones), `flag.trade_restriction{drop, trade, trade_partner, sell, cart, storage, guild_storage, mail, auction}`, `flag.no_refine`, `flag.gradable` |
| Behaviour | `script`, `equip_script`, `unequip_script` (compiled `script_code*`), `flag.delay_consume`, `flag.autoequip`, `flag.buyingstore`, `flag.dead_branch`, `flag.group` (item-group container), `flag.guid` (always gets a unique id), `flag.bindOnEquip`, `flag.broadcast`, `flag.dropEffect`, `stack{amount, inventory, cart, storage, guild_storage}`, `item_usage{override, sitting}`, cooldown/delay ⚠️ |
| Derived | `mob[MAX_SEARCH]` (top droppers, filled from the mob DB), combo links |

`ItemDatabase` (`itemdb.hpp:3554`) is a cached YAML DB. `parseBodyNode` compiles the three scripts with `parse_script` (`itemdb.cpp:1071-1105`). `itemdb_read` (`itemdb.cpp:4872`) loads the item DB and the dependent DBs (combos, groups, random options, Laphine, reform, enchant, packages, roulette).

### `item` (instance)

✅ A packed struct (`mmo.hpp:313`):

- `id`: SQL row id
- `nameid`, `amount`
- `equip`: currently equipped `EQP_*` positions
- `identify`, `refine`, `attribute` (broken)
- `card[MAX_SLOTS]`: card ids. Also reused for special encodings: forged weapons (`CARD0_FORGE`: element, star crumbs, creator char id), pet eggs, named items (`itemdb_isspecial`)
- `option[MAX_ITEM_RDM_OPT]`: random options `{id, value, param}`
- `expire_time`: rental items
- `favorite`, `bound` (account, character, party or guild bound)
- `unique_id`: a 64-bit GUID, generated by `pc_generate_unique_id` when `flag.guid` is set, and used for anti-dupe tracking
- `equipSwitch`, `enchantgrade`

**Fork note:** `itemdb_isidentified(nameid)` (`itemdb.cpp:~3343`) **always returns 1**. Upstream returns 0 for weapons, armour, pet armour and shadow gear. So every newly created item is identified: drops, `getitem`, and anything else that calls it.

## 2. Containers

✅ `struct s_storage` (`mmo.hpp`) is used for **inventory, cart, storage, premium storage and guild storage**. It is a union `u.items_inventory` / `items_cart` / `items_storage` / `items_guild`, plus `amount`, `max_amount`, `dirty`, `stor_id`, `type`. They are all saved through the same `char_memitemdata_to_sql` diffing ([../database-architecture.md §6](../database-architecture.md#6-character-persistence)).

| Container | Key code | Notes |
|---|---|---|
| Inventory | `pc_additem` (`pc.cpp:5991`), `pc_delitem` (`:6103`), `pc_search_inventory`, `pc_setinventorydata` (`:1500`, fills `sd->inventory_data[]` with raw `item_data*`) | `MAX_INVENTORY` slots, plus inventory expansion (`inventory_slots`) |
| Cart | `pc_putitemtocart` (`:6687`), `pc_getitemfromcart` (`:6740`), `pc_cart_additem`/`delitem` | Requires a cart option |
| Storage (account) | `storage_storageopen` (`storage.cpp:133`), `storage_additem`/`delitem`, `storage_storagesave` | Loaded from char on login (`intif_storage_request`). Extra storages are defined in `conf/inter_server.yml` |
| Guild storage | `storage_guild_storageopen` (`storage.cpp:556`) | One user at a time. Persisted by char `int_storage`. `guild_storage_log` |
| Floor | `map_addflooritem` (`map.cpp:2007`), `pc_dropitem` (`pc.cpp:6137`), `pc_takeitem` (`:6189`) | `flooritem_data : block_list` (`BL_ITEM`). Ownership priority (`first/second/third_charid`), cleanup timer `map_clearflooritem_timer` |

### Adding an item: `pc_additem`

✅ `pc_additem(sd, item, amount, log_type, favorite)` (`pc.cpp:5991`) returns an `e_additem_result`: `ADDITEM_SUCCESS`, `INVALID`, `OVERWEIGHT`, `ITEM`, `OVERITEM`, `OVERAMOUNT`, `REFUSED_TIME`, `STACKLIMIT`.

1. Validate the amount and the stack limit (`stack.inventory`) (`+12-18`).
2. Weight: `sd->weight + id->weight * amount > sd->max_weight` → `ADDITEM_OVERWEIGHT` (`+21-23`).
3. GUID: if `flag.guid` and there is no `unique_id`, generate one (`+25-26`).
4. Stackable and not a rental: merge into an existing identical stack (same cards, options, bound, `unique_id`…) and send `clif_additem` (`+29-43`).
5. Otherwise take a free slot (`pc_search_inventory(sd, 0)`), or return `ADDITEM_OVERITEM` (`+51-54`). Copy the item in, update weight and inventory data, send `clif_additem`.
6. Logging (`log_pick_pc`), achievement `AG_GET_ITEM` (`pc.cpp:~6087`), rentals (`pc_inventory_rental_add`).

Callers must handle failure. The usual pattern is to drop the item on the floor (`map_addflooritem`) when `pc_additem` fails, as the `getitem` script command and mob loot do.

## 3. Using items

✅ The client `CZ_USE_ITEM` → `pc_useitem(sd, n)` (`pc.cpp:6450`):

1. NPC-dialog guard: items are blocked during dialogs unless `enable_itemuse` was used (`+15-21`).
2. **`pc_isUseitem(sd, n)`** (`:6276`): type, job, level, map restrictions (`nobranch`, `noitemconsumption`, zones), SC blocks (`sc.cant.consume`), item delays and cooldowns, weight, special cases.
3. Consumption: either delayed (`flag.delay_consume`: the item is consumed after the triggered skill completes, e.g. scrolls and Yggdrasil-type items), or immediate (`clif_useitemack` + `pc_delitem(…, LOG_TYPE_CONSUME)`) (`+44-87`).
4. Run `item_data::script` with `run_script(script, 0, sd->id, fake_nd->id)`, after temporarily detaching any script the player is in (`pc.cpp:~6560-6580`). The script performs the effect: `percentheal`, `itemheal`, `sc_start`, `itemskill`, `getitem`, `getgroupitem`…
5. Item cooldowns: `pc_itemcd_do` (⚠️ item `Delay` fields, not traced in detail).

**Item groups** (boxes, card albums, random rewards): `getgroupitem` / `getrandgroupitem` → `ItemGroupDatabase` (`itemdb.hpp:3596`, `item_group_db.yml`): `get_random_entry(group, subgroup, algorithm)`, `pc_get_itemgroup_sub`. Entries `s_item_group_entry` (`:3414`) carry `rate`, `amount`, `duration` (rental), `isAnnounced`, `GUID`, `isStacked`, … **Item packages** (`item_packages.yml`, `ItemPackageDatabase`) work similarly for official package boxes.

## 4. Equipping

✅ `pc_equipitem(sd, n, req_pos, equipswitch)` (`pc.cpp:12015`):

1. Validate: item type, `pc_isequip(sd, n)` (job, sex, level, map restrictions, SC/state), broken status (`+14-62`).
2. **Bind on equip** (`+69-71`).
3. Resolve the slot: accessories go to the free L/R slot, dual-wield weapons, cards with fixed slots, costume and shadow positions (`+74-100`). Unequip whatever is in the way.
4. Set `item.equip = pos` and `sd->equip_index[...] = n`. `clif_equipitemack(OK)`, look updates (`clif_changelook` weapon, shield, headgear, robe…) (`+154-185`).
5. `pc_checkallowskill` (end SCs whose requirements are no longer met), **`pc_load_combo`** (`:11980`, recompute active item combos; *must* happen before the recalculation), then `status_calc_pc(sd, SCO_NONE)` (`+215-240`).
6. **Run `equip_script`** for the item and its cards (unless `itemdb_isNoEquip` on this map, or the player has `PC_PERM_USE_ALL_EQUIPMENT`), on `fake_nd` (`pc.cpp:~12264`, `:~12275`).

`pc_unequipitem(sd, n, flag)` (`:12398`) mirrors this: it clears the slot, updates the look, re-checks combos, runs `unequip_script` (`:12362`) and recalculates.

`pc_check_available_item(sd, type)` (`:12672`) removes or unequips items that became invalid (after a DB reload, or a map with restrictions).

## 5. Bonuses (how item scripts change stats)

During `status_calc_pc_sub` (see [status-system.md §3.2](status-system.md#32-player-pipeline-status_calc_pc_sub)), the scripts of equipped items, cards, combos and random options run with the player attached. Their `bonus*` commands call into `pc.cpp`:

| Script command | C function | Arity |
|---|---|---|
| `bonus bType, val;` | `pc_bonus(sd, type, val)` (`pc.cpp:3725`) | 1 |
| `bonus2 bType, a, val;` | `pc_bonus2` (`:4498`) | 2 |
| `bonus3` / `bonus4` / `bonus5` | `pc_bonus3` (`:5164`), `pc_bonus4` (`:5305`), `pc_bonus5` (`:5388`) | 3–5 |
| `autobonus` / `autobonus2` / `autobonus3` | `pc_addautobonus` (`:3378`), cleared by `pc_delautobonus` (`:3429`); triggered by `pc_exeautobonus` from skill/battle hit paths | |
| `bonus_script` | `pc_bonus_script` (`:15008`); timed, persisted in SQL `bonus_script` | |

These functions are big `switch (type)` blocks over `SP_*` bonus ids (272 `case SP_` labels in `pc_bonus*`). They write into:

| Destination | Holds |
|---|---|
| `sd->base_status` fields | flat stats |
| `sd->bonus` | rates: `hp_rate`, `aspd_add`, `castrate`, `crit_atk_rate`, … |
| `sd->indexed_bonus` | per race / class / element / size arrays: `addrace`, `subele`, `expaddrace`, … |
| `sd->right_weapon` / `left_weapon` | per-hand modifiers |
| `sd->special_state` | flags: `no_knockback`, `no_gemstone`, `intravision`, … |
| `pc_bonus_autospell` (`:3126`) / `pc_bonus_addeff` (`:3211`) lists | proc effects |

Combat reads these fields (`battle_calc_cardfix` and others, see [combat-system.md](combat-system.md)). `doc/item_bonus.txt` lists every bonus. They are exposed to scripts as constants (`bStr`, `bAddRace`, …) through `script_constants.hpp`.

**Item combos** (`item_combos.yml`, `ComboDatabase`, `itemdb.hpp:3325`): when every item in a set is equipped (`pc_load_combo`), its `Script` runs during the recalculation (`status.cpp:~4056-4086`). This fork adds a Dragon Eye Ring combo (`db/re/item_combos.yml`).

**Random options** (`item_randomopt_db.yml`, `item_randomopt_group.yml`): `RandomOptionDatabase` / `RandomOptionGroupDatabase` (`itemdb.hpp:3379`, `:3396`). Each option id maps to a script with a `value`. ✅ Mob drop entries can name a `RandomOptionGroup` (`mob.cpp:4908`), which is rolled when the item drops (`mob.cpp:2485`). Scripts can also set them (`getitem3`-family commands, `setrandomoption`).

## 9. Customisation guide

| Goal | Where |
|---|---|
| New or changed item, its stats, its bonuses | `db/import/item_db.yml` (bonuses via `Script:` + `doc/item_bonus.txt`). Client-side item info is also needed |
| New combo | `db/import/item_combos.yml` |
| Box / random reward | `db/import/item_group_db.yml` + an item with `Script: getgroupitem(IG_X);` |
| Refine rates and costs | `db/import/refine.yml` (this fork edits `db/re/refine.yml` directly) |
| Cash shop items | `db/import/item_cash.yml` |
| A new `bonus` type | 1) Add `SP_X` to `enum _sp` (`map.hpp:498`), export it in `script_constants.hpp` (`export_parameter`/constant `bX`). 2) Add a field to `sd->bonus` / `indexed_bonus`, **reset at the start of `status_calc_pc_sub`** (it memsets `sd->bonus`). 3) Add a `case` in `pc_bonus*`. 4) Read it where it should take effect (battle or status) |
| Global drop/identify behaviour | `conf/battle/items.conf`, `drops.conf`; this fork hard-codes identify in `itemdb_isidentified` |
| Item restrictions per map | `item_db` `NoUse`/`Trade` flags, `db/re/item_noequip.txt` (zone restrictions, loaded with `sv_readdb` at `itemdb.cpp:4900`, checked by `itemdb_isNoEquip`), mapflags |

Pitfalls:

- `sd->inventory_data[]` holds **raw pointers** into the item DB. After `@reloaditemdb` they are refreshed by `pc_setinventorydata`. Any new raw-pointer caches must be refreshed in `itemdb_reload` too.
- **Item `Script`** runs on every recalculation; **`EquipScript`/`UnEquipScript`** run once per equip/unequip. Put permanent effects in `Script` and one-off effects in `EquipScript`.
- Always check `pc_additem`'s return value. Dropping or refunding on failure prevents item loss.
- `card[]` is overloaded for forged, named and egg items. Use `itemdb_isspecial(card[0])` before treating the values as card ids.
